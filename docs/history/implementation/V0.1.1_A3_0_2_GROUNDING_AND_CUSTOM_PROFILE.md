# V0.1.1-A3.0.2：Grounding 加固与自定义 LLM Profile

## 范围

本轮沿用固定 Orchestrator、确定性水质诊断、TF-IDF 检索和 OpenAI-compatible Adapter。正式项目只读；未引入向量数据库、Agent、Tool Calling 或新模型能力。

## 原问题与根因

`low_oxygen` 场景的现场观测只有水温 28 ℃、pH 7.5、溶氧 2.2 mg/L；确定性规则为 `OXYGEN_CRITICAL_LOW`。此前一次真实 Qwen 结果据使用者反馈，将检索到的车轮虫病、鳃霉病、爱德华氏菌病等背景条目写进了现场推断，并给出具体药物建议。仓库中没有保存那次模型的完整响应和 Usage，因此此处不补写原文或数值。

代码核对发现两个直接原因：

1. 检索将当前数值、用户问题混成查询，且关键词加分与 TF-IDF 分数未按用户意图约束疾病条目。原 `low_oxygen` 页面查询的前五条证据中有三条疾病知识。
2. 旧 Prompt 将证据并列提供给模型，却未明确说明疾病知识是背景资料，不能单独证明现场患病；输出合同虽分开 `inference`、`recommendations` 和 `uncertainty`，没有疾病证据边界。

这是检索相关性和生成 Grounding 的组合问题。不能由“检索到了治疗文本”推断现场已经患病。

## RAG 修改

- 保留现有 `char_wb` TF-IDF、2–4 gram、最多 2000 特征、查询扩展、关键词加分、0.04 最低分与关键词后备检索。
- 根据原始用户问题识别宽泛的水质或疾病意图；确定性规则编码、消息和所用事实进入检索查询，但不把规则中的疾病词误判成用户疾病意图。
- 水质意图对 `water_quality` 和 `relationships` 小幅加权；没有明确疾病意图时将 `disease` 分数降权；明确疾病症状或疾病问题仍可检索疾病条目。关键词加分要求完整关键词命中，不再用过短子串扩大匹配。
- 这是有限的类别排序策略，不是病害检测器，也不保证所有开放问题的最优排序。未改知识 JSON 和来源元数据。

离线页面查询“当前水质情况怎么样？”的修正后前五条为：`wq_dissolved_oxygen`、`wq_ph`、`relationships`、`wq_ammonia_nitrogen`、`feeding_rate`，没有疾病条目。得分只用于相对排序，不代表证据真实性或诊断置信度。

## Grounding 与建议边界

Prompt 与页面现在分别标识 `Observed Facts`（当前观测）、`Rule Results`（程序判断）、`RAG Evidence`（背景知识）、`Inference`（模型推断）、`Recommendations`（模型建议）及 `Uncertainty`（缺失信息）。Prompt 明确要求：没有鱼体症状、检测或其他直接证据时不得诊断具体疾病；没有足够疾病证据时不得直接推荐具体药物、剂量或治疗方案。可以建议观察、取样检测、显微镜检查；优先处理已确认的严重低氧。

程序仍将模型输出按现有 JSON 合同解析，不会把模型建议改写为确定性规则。页面将建议标为“模型建议（待核查）”，并将 Raw Model Output 放入折叠的调试区域。**Prompt 约束不能保证任意真实模型都遵守**；本轮没有建立药物名审核器或人工审批机制。

## CUSTOM Profile 设计与使用

页面“添加 CUSTOM Profile”可填写显示名、`provider_id`、`adapter_id`（`openai_chat` 或 `generic_openai_chat`）、`base_url`、`model`、`secret_env` 环境变量名及 Cloud/Local 类型。状态固定为 `CUSTOM`；生成、推理、流式、结构化输出和 Tool Calling 等高级 Capability 均保持 `UNKNOWN`，不提供 `extra_body`。通用 Adapter 仍按现有合同约束。Built-in Profiles 和 User Custom Profiles 在选择框中分组。

每个自定义 Profile 单独保存为当前工作目录下被 Git 忽略的 `outputs/custom_profiles/custom-<随机标识>.json`；重启 Web 服务时重新加载，不修改包内预置 Profile。保存仅允许上述连接字段、生成的 Profile ID、固定状态和零重试；拒绝额外 `api_key` 字段。配置只含 `secret_env` 名称，不含 Secret 值。真实 Secret 来自进程环境或启动时读取的本地 `.env`。若保存 Profile 后才让它引用 `.env` 中的变量，需重启 Web 服务加载该变量。变量缺失时返回安全错误 `SECRET_MISSING`，不会创建模型请求。

页面默认 Mock 离线；任何自定义 Cloud/Local 真实请求仍需勾选 `REAL NETWORK REQUEST`。当前是单用户本机开发页面，只监听 `127.0.0.1`，没有账号与 Profile 编辑/删除功能。

## 验证结果与前后对照

| 检查 | 修正前 | 修正后 |
|---|---|---|
| Mock `low_oxygen` 证据 | 前五条中三条为疾病知识 | 前五条以溶氧、水质和关联知识为主；无疾病条目 |
| 确定性规则 | `OXYGEN_CRITICAL_LOW` | 保持 `OXYGEN_CRITICAL_LOW` |
| Prompt 边界 | 未明确疾病背景不能作为诊断 | 明确区分事实、规则、背景证据、推断、建议与不确定性 |
| Mock 结构化结果 | 由 MockGateway 返回 | 页面请求 HTTP 200，解析成功；Mock Usage 为 `unavailable` |
| 真实 Qwen 推断、建议、不确定性 | 使用者报告出现无依据疾病和药物建议；无完整原文 | 本轮**无法确认**，见下文 |

本轮先运行完整离线测试，**63 项通过**；随后使用 Flask 测试客户端运行 Mock `low_oxygen`，HTTP 200、结构化解析成功、规则和上述证据排序正确。最后仅进行**一次**真实 Qwen `low_oxygen` 请求：Secret 状态为 `PRESENT`，Profile 与 SDK/Gateway 自动重试均为 0，页面分析返回 HTTP 200。终端在打印返回内容时因 Windows GBK 无法编码模型文本中的字符而抛出 `UnicodeEncodeError`；临时测试数据随进程退出被清理。因此本轮没有可靠留存真实模型的推断、建议、不确定性或 Token Usage，不能声称真实模型已遵守药物边界，也不能完成这些字段的定量前后对照。遵守“一次真实请求”限制，未重发。

## 测试与安全

- 新增 Grounding、显式疾病意图、自定义 Profile 持久化/重载、非法字段拒绝、缺失 Secret、页面折叠区测试；Web 测试的配置目录隔离到临时目录。
- 完整离线命令：`.\.venv\Scripts\python.exe -m unittest discover -s tests -v`；结果：**63/63 通过**。测试阻断 socket 连接与 DNS，真实 Cloud 不进入自动测试。
- `.env`、生产项目、包内预置 Profile 均未修改；没有 commit 或 push。

## 限制与后续

1. 真实 Qwen 输出质量尚未完成可留存的前后对照。后续若另行授权，应使用 UTF-8 输出或只写脱敏后的本地记录，再进行单次受控复测；本轮不再调用。
2. 基于少量关键词的意图分类对复杂混合问题仍可能误排；需要固定问句集评估，不能把排序分数当作临床证据。
3. Prompt 无法构成硬性药物安全保证。涉及实际治疗决策需现场证据与专业人员复核。
4. 自定义 Profile 暂不支持编辑、删除、Capability 验证和 UI 高级参数；新 `.env` 引用需要重启。
