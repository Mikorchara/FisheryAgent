# V0.1.1-A2 DeepSeek 真实 Cloud API 验证报告

后续 Model ID 对齐、能力合同修正与网络诊断见 [A2.1 报告](V0.1.1_A2_1_DEEPSEEK_COMPATIBILITY_AND_NETWORK_DIAGNOSTICS.md)。本页保留 A2 当时的请求配置与实测结果。

日期：2026-09-29（Asia/Shanghai）。本轮**部分完成**：最小请求、Reasoning AUTO 与 ON 成功；随后连续三次请求尝试在连接/超时阶段失败，故停止进一步真实调用。状态词仅描述本轮证据，不代表 DeepSeek 所有模型或以后版本的能力。

- 执行位置：Prototype 工作区的 Windows PowerShell、项目 `.venv`，Python 3.12.14。

## ACTUAL API CALL COUNT

本轮 **6 次 Chat Completions SDK 请求尝试**：3 次得到成功响应，3 次连接/超时失败。每次入口只发起一个请求，自动重试为 0。失败尝试是否到达服务端或产生计费不可从本地错误断定；下表只累计 Provider 实际返回的 Usage。未调用模型列表接口、错误模型接口、流式接口或 Fishery 全链路。

| 顺序 | 检查 | SDK 请求尝试 | 结果 | 总耗时 |
| --- | --- | ---: | --- | ---: |
| 1 | 最小 Chat Completion | 1 | 成功，正文非空 | 5047 ms |
| 2 | Reasoning AUTO | 1 | 成功，正文非空 | 1922 ms |
| 3 | Reasoning ON | 1 | 成功，正文非空 | 1860 ms |
| 4 | Reasoning OFF | 1 | `CONNECTION_OR_TIMEOUT`，无 Provider 响应 | 6031 ms |

连续三次无 Provider 响应后停止，避免反复尝试造成不确定费用。本轮没有继续做温度、top_p、输出上限、流式、错误模型或全链路请求。

## MODEL ID VALIDATION / BASIC CHAT COMPLETION

第一条请求只发送简短 `messages` 与配置模型 ID；没有添加思考控制、temperature、top_p、输出上限或流式参数。Gateway 成功读取非空正文，Provider 返回 `deepseek-flash` 与完整 Usage。结论：**配置的旧 ID 当前可调用，但实际服务的是新版 Flash**；不能把旧 ID 的名字当成固定模型版本。官方 [Chat Completions 文档](https://api-docs.deepseek.com/api/create-chat-completion/)当前列出 `deepseek-flash` 与 `deepseek-v4-pro` 为推荐 ID。

## REASONING AUTO / ON / OFF / EFFORT

- **AUTO：VERIFIED（本次请求）**。适配器未发送思考开关，响应有正文、可选 `reasoning_content` 与 reasoning token Usage；与官方文档的默认思考模式一致。
- **ON：VERIFIED（本次请求）**。实验探测临时将能力视为支持，适配器发送 `thinking.type=enabled`；响应有正文、`reasoning_content` 和 Usage。没有把临时探测能力持久化到 Profile。
- **OFF：FAILED（本轮两次请求）／能力仍 NOT VERIFIED**。适配器映射 `thinking.type=disabled`，但两次均出现 `CONNECTION_OR_TIMEOUT`，没有 HTTP 参数拒绝响应，也没有正文或 Usage。不能据此断定 OFF 不受支持。官方[思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)说明此开关存在；仍需网络稳定后做本项目实测。
- **Effort：FAILED（本轮一次请求）／能力仍 NOT VERIFIED**。官方 [Chat Completions 文档](https://api-docs.deepseek.com/api/create-chat-completion/)列出 `low/high/max` 作为当前思考档位；本轮仅尝试 `low`，连接/超时失败，未取得 Provider 响应。不能称该档位在本项目已通过。

本轮暴露一个合同细节：现有单个 `reasoning_toggle` 三态无法同时表达“ON 已实测、OFF 未实测”。因此不宜直接把整个 Toggle 标为 SUPPORTED。后续可用最小改动分别声明允许的模式或 ON/OFF 支持状态；本轮不因一次 ON 成功而放宽 OFF 的普通业务路径。

## CAPABILITY CHANGES RECOMMENDED

1. 保留当前 Profile 为 **EXPERIMENTAL**，不把临时 Probe 的 Capability 写回静态配置。最小 Chat Completion、AUTO 默认行为和 ON 的实测结果在报告中分别记录。
2. 如果以后要把 ON 加入普通业务路径，先让 Capability 合同能区分 ON 与 OFF；不要把目前单个 `reasoning_toggle` 直接标为全支持。
3. 根据官方资料，可把“思考开启时 temperature 无效”列为明确的参数冲突政策；普通业务仍须在显式 ON + temperature 时给 `OPTION_CONFLICT`，不得透传或静默丢弃。
4. `top_p` 的模式与有效范围、`max_tokens` 原始字段、effort 的合法值可作为官方文档线索；实际映射到此旧请求 ID 与服务版本的行为须后续单项复核。Streaming、structured output 和 tool calling 均不因本轮请求成功而自动变成 SUPPORTED。

## PROFILE PROMOTION RECOMMENDATION

**KEEP EXPERIMENTAL。** 理由：旧 Model ID 已被官方声明为暂时兼容路由，返回的是新模型 ID；OFF 与 effort 未取得成功响应，参数、流式、Fishery 全链路与错误映射尚未验证。建议用户先确认是否批准把请求 ID 从 `deepseek-v4-flash` 更新到官方当前 `deepseek-flash`；本轮没有自行更改。

## RISKS

- 三次失败的请求是否到达 Provider、是否计费无法从客户端确认，故 Token 合计仅覆盖三次成功响应。
- 官方接口文档会随模型更新变化；本轮看到的是 2026-09-29 的资料。报告明确区分官方声明、本项目实测与未验证。
- 当前 `GatewayError` 将连接异常和超时合并；如果后续仍持续发生，需要用脱敏的传输诊断区分 DNS、TCP、TLS、代理和读取超时，不应输出原始异常或 Secret。
- 新真实入口会联网并可能产生费用；必须显式传 `--confirm-network`。Profile 没有自动 failover，默认 Demo 与测试保持离线。
