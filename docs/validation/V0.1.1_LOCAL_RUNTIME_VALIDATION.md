# Fishery AI Prototype V0.1.1：本地运行时验证计划

阶段名称：**Local Runtime Validation（本地运行时验证）**

文档性质：后续工作站验证的执行计划；本文不记录已完成的真实模型测试。

## 1. 阶段目标

V0.1 已具备 Domain Contracts、固定 Mock 数据、确定性水质诊断、TF-IDF RAG 基线、ModelGateway、Cloud/Local Profile、OpenAI SDK 适配器、AnalysisResult、JSONL Trace 和离线测试。Mock 测试证明了这些组件在受控输入下能够协作，**Mock 验证成功 ≠ 真实 Local LLM 已验证**。真实服务还会带来模型加载、接口差异、流式事件、超时、输出格式和性能问题。

V0.1.1 的目标是在工作站上验证现有架构连接真实 OpenAI-compatible 本地及 Cloud LLM 的能力，优先验证本地模型；不以增加产品功能为目标。每项结论都要记录实际 Runtime、模型版本、输入场景和证据，未执行的检查标记为“未验证”。

本阶段不设计或实现 Tool Calling、Agent Loop、Memory、Fine-tuning、Vector Database、生产 Fishery Adapter、YOLO Integration 或数字人。正式项目 `D:\Fishery_Project` 始终只读。

## 2. 当前架构位置

```text
Fishery AI Orchestrator
          ↓
ModelGateway 合同
          ↓
OpenAICompatibleAdapter
          ↓
OpenAI Python SDK
          ↓
Local OpenAI-compatible Runtime
          ↓
Local Model
```

当前 `Orchestrator.analyze()` 调用 `gateway.complete()`；适配器另有 `stream()`，但应用编排尚未使用它。`build_offline_demo()` 始终注入 `MockGateway`，即使选择 `local-demo` 也不会调用本地服务。因此真实全链路验证须在后续执行阶段使用受控的验证入口装配现有组件并注入真实适配器；不能将现有 Mock CLI 输出作为真实模型证据。若必须修改产品代码才能完成装配，应先单独记录缺口并评审，不在本文中预设新架构。

## 4. Local Runtime 候选

下表是**基于官方文档的候选比较与本项目的实施推断**，不是本工作站实测结果。工具调用列仅评估未来兼容性，本阶段不发送工具定义、不执行工具。

| 候选 | Windows 使用难度 | OpenAI-compatible API 与 Streaming | 未来 Tool Calling 兼容性 | GPU 支持与部署复杂度 |
| --- | --- | --- | --- | --- |
| Ollama | 较低：官方提供原生 Windows 应用。 | 提供 `/v1/chat/completions`，官方列出流式支持；仍需实测本项目 SDK 的事件与 Usage。 | 官方列出工具支持；实际效果取决于模型及接口实现，V0.2 再验证。 | 官方说明 Windows 支持 NVIDIA/AMD；安装和首次验证步骤相对少。参见 [Windows 文档](https://docs.ollama.com/windows)与[兼容 API 文档](https://docs.ollama.com/api/openai-compatibility)。 |
| llama.cpp server | 中等：有 Windows `llama-server.exe`，但需要准备匹配的可执行文件、模型和参数。 | 官方提供 `/v1/chat/completions` 与同步/流式响应；兼容性边界仍需实测。 | 官方文档支持函数调用，但可能依赖 Jinja 聊天模板和启动参数。 | 支持 CPU/GPU 与量化模型，GPU 构建、模型格式和参数需自行管理。参见 [官方 server 文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)。 |
| vLLM | 在 Windows 上较高：官方说明不支持原生 Windows，可考虑 WSL/Linux。 | 提供 OpenAI-compatible Chat Completions 和流式服务。 | 官方支持多种 Tool Calling 模式，但需要对应模型、模板或解析器配置。 | 适合后续更复杂的 GPU 服务验证；当前最小 Windows 验证的部署步骤较多。参见 [安装要求](https://docs.vllm.ai/en/latest/getting_started/installation/gpu/)、[在线服务](https://docs.vllm.ai/en/latest/serving/openai_compatible_server/)与[工具调用说明](https://docs.vllm.ai/en/latest/features/tool_calling/)。 |

**第一轮建议**：若目标工作站满足官方要求，可用 Ollama 做最小本地验证。它只是第一轮测试对象，**不是永久架构依赖**。`ModelGateway` 与业务层必须保持 runtime-neutral；更换服务时只调整 Profile 和适配器边界内的兼容配置，不向 Orchestrator 添加服务名称分支。

## 5. 模型选择原则

不预先指定永久模型。先按工作站可用资源筛选候选，再记录实际测试结果：

1. 中文水产养殖问题的理解、术语表达和指令遵循。
2. 在固定输入下输出当前要求 JSON 的稳定性；是否频繁多写解释或代码围栏。
3. 模型文件大小、量化方式、显存需求、上下文长度与可接受的推理速度。
4. 所选运行时能否通过 OpenAI-compatible Chat Completions 使用该模型。
5. 后续 Tool Calling 的潜力；只作为选型记录，不作为 V0.1.1 实施内容。

候选模型名、许可证、版本和量化信息以工作站实际安装版本为准。比较时固定问题、场景与生成参数；如参数无法在不同服务中等价设置，明确记录差异。

## 6. API 基础验证

先检查服务接口，再连接项目全链路。请求统一使用记录过的 `base_url` 和实际模型 ID；`/v1/chat/completions` 是必测接口。服务专用健康接口或 `/v1/models` 可作为辅助，不替代 Chat Completions 验证。每项记录 HTTP 状态、响应格式、耗时和错误码；不保存敏感请求头。

| 用例 | 操作 | 预期观察 |
| --- | --- | --- |
| Test A：Local server reachable | 启动选定服务后检查其监听地址及可用的健康或模型列表接口。 | 服务可达，记录地址和 Runtime 版本；不把仅端口可达当成模型可用。 |
| Test B：`/v1/chat/completions` | 用已安装模型与最小 `messages` 发送请求。 | 路由存在，返回可识别的 Chat Completions 结构。 |
| Test C：non-stream completion | 设置 `stream=false`，读取正文及可选 Usage。 | `choices[0].message.content` 为字符串；记录模型身份、耗时和 Usage 可用性。 |
| Test D：streaming completion | 设置 `stream=true`，逐个读取事件。 | 至少出现一个非空正文 delta，并正常结束；记录事件顺序和 Usage 是否返回。 |
| Test E：invalid model | 使用明确不存在的模型 ID。 | 返回可解释的失败；记录实际 HTTP 状态及 Gateway 错误码，不预设所有服务相同。 |
| Test F：server unavailable | 停止测试服务或改用确认未监听的本地端口。 | 在配置的连接超时与重试策略内失败，不产生伪造正文。 |
| Test G：timeout | 使用可控的延迟场景触发读取或总时限。 | 记录实际耗时、重试次数和错误分类；若无法稳定制造延迟，标为未验证。 |

当前 Profile 默认 connect 5 秒、read/stream idle 30 秒、total 120 秒、最多重试 1 次；验证时记录是否使用这些值及任何临时覆盖。错误注入只作用于测试服务，不触碰生产项目。

## 7. Fishery_AI_Prototype 全链路验证

```text
Mock Water Quality
        ↓
DiagnosisService
        ↓
TF-IDF RAG
        ↓
Orchestrator
        ↓
ModelGateway → 真实 Local Profile / Local LLM
        ↓
AnalysisResult
        ↓
JSONL Trace
```

使用项目自带的固定 `normal`、`low_oxygen`、`partial`、`stale`、`partial_stale` 水质场景。验证执行阶段应复用现有仓库、诊断、检索、编排和 Trace，只在网关装配处注入 `OpenAICompatibleAdapter` 与工作站上的真实 Local Profile；`local-demo` 的模型名仍是占位符，不能直接当作真实模型。验证入口应明确标记为“真实连接”，与现有离线 Demo 区分；本轮仅写计划，不创建该入口。

逐次核对：

- `observed_facts.water_quality` 的值、时间、质量与新鲜度仍来自 Mock 数据；`rule_results` 仍来自确定性规则；`evidence` 的 ID、来源与分数来自检索。模型不得重写这些事实。
- `generated_text` 保留模型原文；`inference`、`recommendations`、`uncertainty` 与 `structured_parse_ok` 符合解析结果。解析失败时原文保留且标记失败。
- `runtime` 中的 Profile/模型身份对应请求开始时的 Snapshot；`status`、可选 `usage`、`request_id` 与 `trace_id` 可追溯。
- JSONL Trace 的规则码、证据 ID、输入快照元数据、状态、耗时和错误码与结果一致；不记录 Key、完整 Prompt 或模型正文。

## 8. Cloud / Local 切换验证

使用相同的 Mode、问题、Mock 场景、Domain Logic、RAG 和 Orchestrator，只改变 `AnalysisRequest.profile_id` 及其解析到的 Profile/Runtime；`AnalysisRequest` 本身含有 `profile_id`，因此两个请求对象除该字段外才是相同输入。记录 Cloud 与 Local 的实际 `base_url`、模型名、状态、输出格式和 Trace 对应关系。

首先以 Mock 确认路由切换；再分别进行经授权的真实 Local 和真实 Cloud 请求，才能声称两种服务均已验证。若 Cloud 访问尚未获授权或密钥不可用，只记录“Profile 路由已验证，Cloud 真实连接未验证”，不得将其计为完整通过。真实 Key 只从环境变量读取，不写入 Profile、文档或 Trace。业务层不得出现 `if Ollama`、`if DeepSeek` 等服务专用分支。

## 9. Streaming 验证

**Gateway streaming validation（本阶段）**：直接对适配器的 `stream()` 做受控真实服务验证，记录首个非空 delta、连续 delta、可选 Usage、正常结束和中途失败。分别检查首个正文输出之前的可重试错误，以及正文已输出后的失败：后者不得自动重新生成。服务是否在流式模式提供 Usage 由实际实现决定；缺失时记录“不可用”，不虚构令牌数。

**Future application streaming integration（后续）**：当前 `Orchestrator.analyze()` 只调用 `complete()`，尚无面向用户的应用层流式编排。本阶段 Gateway 流式通过，不代表 Chat/Advice UI 已具备流式输出。用户取消后的资源释放、部分结果与 Trace 语义列为后续研究点，不在 V0.1.1 实现。

## 10. 性能指标

同一场景至少记录一次完整真实请求；建议区分首次加载与模型已热身后的重复运行，避免混合比较。计时点与数据来源须一并记录。

| 指标 | 记录方法 |
| --- | --- |
| TTFT | 从发起流式请求到**首个非空正文 delta** 的时间；标明是否包含模型冷加载。 |
| Total Latency | 从请求发起到完整响应或流正常结束的时间；全链路耗时另列，不与模型调用耗时混写。 |
| Output Tokens | 优先使用服务返回的 completion tokens；不可获得时注明“不可用”或注明所用模型 tokenizer 的估算方法。 |
| Tokens / Second | 用上述输出令牌数除以明确记录的生成耗时；标明令牌数来源和是否为估算。 |
| Prompt Tokens / Completion Tokens | 服务提供 Usage 时分别记录；没有返回时留空。 |
| Peak VRAM | 若工作站可测，记录工具、采样区间与单位；不可测时留空。 |
| 模型加载时间 | 能区分冷启动时单独记录；无法区分时说明。 |

## 11. 输出质量检查

使用固定场景和问题，保存可复核的结果摘要，不把模型回答当成传感器或检索事实：

| 场景 | 固定问题 | 检查重点 |
| --- | --- | --- |
| `normal` | 当前水质是否正常？ | 不虚构告警、额外传感器值或检测事件。 |
| `low_oxygen` | 溶氧偏低可能有什么影响？ | 正确引用程序给出的溶氧事实、规则结果及可用证据；建议与证据分开。 |
| `partial` / `partial_stale` | 当前数据不足时应该如何表达？ | 明确缺失和过期，保留不确定性，不补造 pH 或观测时间。 |
| 无检索证据的受控输入 | 没有相关知识证据时依据是什么？ | 不编造来源 ID、文献或“已检索”结论。若当前固定场景不能产生空证据，应标为专项待验证，不伪称全链路已覆盖。 |

逐项核对 Facts、Rule Results、Evidence、Inference、Recommendation、Uncertainty 的来源边界。记录错误示例的类别和复现条件；不要将原始敏感 Prompt 写入 Trace。

## 12. JSON / Structured Output 验证

在真实模型上记录当前提示要求的 `inference` 字符串、`recommendations` 字符串数组和可选 `uncertainty` 字符串数组的返回情况：

- **valid JSON**：纯 JSON 能解析，`structured_parse_ok=true`。
- **markdown fenced JSON**：完整的 JSON 代码围栏能解析，`structured_parse_ok=true`。
- **invalid structured output**：语法或字段类型错误时保留 `generated_text`，`structured_parse_ok=false`，并记录出现频率与具体类别。

同一固定问题至少重复测试，统计各类结果，不在 V0.1.1 提前加入复杂 JSON 修复或再次调用模型修复。若输出结构不稳定，先记录模型、运行时和提示版本，再决定是否另开改进任务。

## 13. Error / Timeout Validation

| 故障 | 预期核对 |
| --- | --- |
| 服务不可用 / 连接拒绝 | 已知 SDK 连接异常应映射为 `CONNECTION_OR_TIMEOUT`；检查重试次数、最终耗时和结构化失败结果。 |
| 无效模型 | 检查实际 HTTP 状态及相应 `HTTP_<status>` 错误码，避免假定所有服务都返回相同状态。 |
| 读取超时 | 检查是否归类为 `CONNECTION_OR_TIMEOUT`；区分服务首字慢、流中空闲和模型加载。 |
| 总时限 | 检查 `TOTAL_TIMEOUT` 或实际 SDK 超时结果；当前总时限并非硬实时截止，记录偏差。 |
| 畸形响应 | 检查是否产生 `INVALID_RESPONSE`、`INVALID_STREAM_EVENT` 或未映射异常；后者应作为兼容性缺口记录，不在本计划中擅自改代码。 |

`Orchestrator` 目前只把 `GatewayError` 转为失败 `AnalysisResult`。因此除了记录错误码，还要确认错误确实到达网关边界、没有把密钥或服务原始错误正文写入 Trace。若兼容服务返回了适配器未覆盖的异常，应标记验收缺口，另行评审修复。

## 14. 验收标准

只有以下条件均有记录和证据时，才宣布 V0.1.1 验证完成：

1. 真实 Local LLM 至少完成一次 Chat Completions 请求，并在固定水质场景中产生正常的 `AnalysisResult`；关键场景的事实、规则和证据边界经人工核对。
2. 使用同一编排流程切换 Cloud/Local Profile，不修改 Orchestrator 业务流程。若 Cloud 真实调用未获授权，阶段结论必须明确保留“Cloud 真实连接未验证”，不得宣称两端均通过。
3. Gateway 的真实流式请求出现首个正文 delta、连续输出并正常结束；记录中途失败及“正文已输出后不重试”的验证结果。不得把 Gateway 流式通过写成应用层流式已完成。
4. `generated_text`、结构化字段、`structured_parse_ok`、Runtime 元数据和 JSONL Trace 可对应；Trace 不泄漏 Secret。
5. 至少有一组标注计时起止点和令牌来源的 TTFT、Total Latency、Tokens/s 数据。
6. API 基础验证与错误/超时用例有逐项结果；未能稳定复现的用例明确标为未验证，不以推断代替测试。
7. 所有原有离线测试继续通过，且真实连接验证不改变默认离线测试行为。

若必要用例未通过，保留实际结果、阻塞点和建议的最小修复，不降低验收口径。

## 16. V0.1.1 之后

本阶段完成后，才进入 **RAG Evaluation** 和 **V0.2 只读 Tool Calling** 的具体设计。Fine-tuning 须等待明确任务、额外数据和评估基线。Agent Loop 不会因本地模型可用而自动进入实施阶段；Memory、生产项目适配器、YOLO 和数字人也保持后续议题。
