# 失联风险的人工结束（Prototype 实验版）

2026-10-23：仅在 Prototype/apps 实现，等待人工验收，未同步 Management。没有改动真实实例、Credentials、Policy、AI Tool、监测阈值或视觉三窗恢复。

2026-10-24复核：补充校时回退、不同请求并发、视觉三窗/新Session、ACK删除绕过和DTO证据限幅验证。修复校时后较早时间戳的新操作被旧操作盖过的问题：每周期按单调人工revision判断最新操作，原服务器时间不改写，无revision的旧JSON仍兼容，不改Schema。同步结果以Management自身验收记录为准。

## 使用方式

事件详情中，符合条件时出现 **人工结束此风险**。填写1–200字原因，核对涉及的原始记录数后确认。记录本机操作时间和原因，操作来源为“本机操作（未认证访客）”，不伪造工作人员身份。

- 仅处理观测过期、离线、缺测或无效导致的待核实风险；同周期只要还有可靠 ACTIVE 异常或恢复观察，就拒绝。明确仍在命中的数据质量告警不属于这一版的人工结束范围。
- 有稳定风险周期则处理整个周期；旧记录只有 inferred/legacy-* 时，只处理选中的单个原始ID，不凭猜测合并。
- 首页当前异常不再重复展示有效人工结束的提醒；历史列表仍可查看，并可筛选“已人工结束”。人工结束时间单列标明，不填入规则恢复时间。
- 不删除原事件，不改 ACTIVE/INDETERMINATE/RESOLVED、不删除 alerts 链接、不修改观测/历史/ACK；后台规则继续监测。缺少可靠新观测时，页面仍显示状态未知，不能把首页安静等同正常。
- 新一次可靠 HIT 更新观测/批次，或增加新等级、改变规则身份后，原人工结束不再压住提醒；同周期历史仍保留。可靠 CLEAR 最终达到规则恢复条件后，按原逻辑显示已恢复。

## 状态关系

| 条件 | 列表显示 | 监测事实 |
|---|---|---|
| 异常有新鲜可靠证据 | 异常中 | 原 ACTIVE，不允许人工结束 |
| 失联等原因无法确认当前风险 | 状态待核实 | 原 INDETERMINATE，可按条件人工结束 |
| 操作者结束这段旧提醒 | 已人工结束 | 仍保留原监测状态，恢复时间为空 |
| 后续再次可靠检出 | 异常中 | 提醒重新出现，保留人工历史 |
| 达到原规则恢复条件 | 已恢复 | 原 RESOLVED，人工历史不冒充恢复证据 |

ACK与人工结束独立：人工结束不代做ACK，已人工结束的提醒不能新增ACK；原幂等ACK重放不产生新操作。没有新增AI写入Tool、派单、Snooze或批量“一键结束全部”。

## 持久化、安全与留存

- Schema保持v2；使用现有 events.payload 的 `manual_ends` 追加记录，不新增表或启动迁移。每次记录请求ID/请求摘要、服务器时间、原因、本机来源、成员ID和当时证据快照。
- 周期成员镜像同一份记录，按request_id去重、人工revision排序，避免依赖墙上时钟判断最新操作；新等级入库时同步人工历史，新风险周期不继承。每周期最多50次人工结束，达到后拒绝新操作，不静默裁掉记录。已有事件继续兼容读取。
- POST `/api/events/manual-end-preview` 只接收event_id；POST `/api/events/manual-end` 严格接收event_id/revision/request_id/reason。复用Host、Origin、本机地址、JSON限额及X-Management-Events门禁，浏览器不能指定时间、操作者或监测状态。
- 提交 BEGIN IMMEDIATE 内重新读取原始成员、当前通道观测、联系时间和服务端评估。revision绑定成员/原始payload/通道快照；旧revision、新观测、错误ID、可靠异常、权限不足均拒绝。相同幂等请求返回原结果，重用请求ID改参数拒绝；SQL失败整笔回滚，无网络调用进入事务。
- 人工历史及关联原始事件不参加普通单条/批量删除、ACK整周期删除或300条自动裁剪。此次没有开放人工结束记录的永久删除。保留提醒收尾证据是明确的数据政策，不能把人工结束描述成清空数据库。
- 旧版代码能读取原事件字段，但不理解人工结束；回退前必须停写并备份，不能让旧版自动裁剪含人工记录的库。后续同步Management需按流程独立回归；不需要v2→v3维护，也不能重新初始化现有库。
