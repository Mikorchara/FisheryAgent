## 先读这一页：问题与建议

1. **截图中的记录确实删不掉。** 两条记录都已经 RESOLVED，但同属一个有 ACK 历史的风险周期；当前策略保护整个周期，不允许普通删除。
2. **ACK 不等于处理完成，也不等于恢复。** 现在把这几层概念同时放在列表中，用户需要理解太多内部规则。
3. **同一次低氧显示两行，是按等级 code 保存历史的结果。** 当前首页异常概况已按风险族整合，但历史列表仍按底层事件行展示。
4. **之前的旧格式修复没有解除 ACK 留存保护。** “旧版记录无法复核”和“已确认周期禁止删除”是两种不同原因。
5. **推荐下一版：一个风险周期一行，已结束后可以归档。** 默认页面简洁，等级变化和 ACK 历史放进详情；归档只移出日常列表，可查看、可恢复，不删除数据库内容。
6. **如果真正需要永久删除，也可以重新设计。** 这是留存策略选择，不是技术上永远不能改变；但必须同时处理 ACK 历史、周期成员及外键，不能只去掉一个“不可删除”判断。

当前实现遵守了 EVT-3A 当时要求的审计保护，但缺少“保留证据，同时让日常列表变干净”的操作出口。单纯再换一轮文案不能完整解决这个体验问题。

## 一、当前机制到底保存了什么

### 1. 四个容易混淆的概念

| 概念 | 实际含义 | 例子 |
|---|---|---|
| 单条事件 | 同设备、同通道、同 code 的异常记录，有独立事件 ID | `OXYGEN_LOW`、`OXYGEN_CRITICAL_LOW` 各一条 |
| 风险周期 | 同一轮风险在不同等级之间变化的关联身份 | 一轮“偏低 → 严重 → 恢复”的低氧过程 |
| 观测状态 | Monitoring 根据可靠数据判断异常、证据不足或消退 | ACTIVE / INDETERMINATE / RESOLVED |
| 人工知晓 ACK | 用户明确表示已看到当时周期和等级的风险 | 已知晓、升级后重新待确认、历史确认记录 |

水质周期使用已持久化的 `risk_family.episode_id`，ACK 还绑定设备、通道、规则身份和等级版本。视觉等单 code 风险使用事件 ID 等身份计算周期。旧 `legacy-*` 推断身份不能直接用于写入 ACK。

### 2. 当前页面文案与操作

| 页面内容 | 含义 | 能否 ACK / 删除 |
|---|---|---|
| 异常持续 | 当前规则仍命中 | 稳定的当前周期／等级可 ACK；不可删除 |
| 恢复观察中 1/3、2/3 | 视觉可靠 CLEAR 尚未达到三窗门槛 | 仍未结束；不可删除 |
| 恢复状态待确认 | 证据不足，或旧等级／规则需要保守表达 | 不等于等待人工点“恢复”；不可直接删除未结束记录 |
| 监测数据中断 | 存在离线或明确缺失通道等证据 | 不作为恢复证据；ACK 与观测状态独立 |
| 规则条件已消退 | 可靠观测满足当前恢复条件 | 不新增 ACK；是否能删除还要检查引用和审计保护 |
| 历史已知晓 | 已结束周期曾有 ACK | 不是人工处理完成；当前受审计保护 |
| 旧版已结束（未复核） | 原始旧记录标记 closed，但无法按新版规则复核 | 不补造 ACK/RESOLVED；结束信息有效且无保护关联时可确认清理 |

水质规则沿用原有 CLEAR 判定；连续三个可靠 CLEAR 是视觉异常的本地实验恢复机制，不是所有事件统一等三窗。新 Session 本身不能证明恢复，但新 Session 中可靠、有效的水质恢复观测可以成为恢复证据。

### 3. 当前 ACK 的重要后果

- 同等级持续异常保留知晓状态；等级变化后保守地重新待确认，旧确认历史保留。
- 规则消退后，页面显示“历史已知晓”；再次发生的新周期不继承旧 ACK。
- 首次 ACK 后，整个周期的现有及后续等级成员都受到保护，不只是被点击的那一行。
- 当前没有 Snooze、人工处理完成、归档、取消归档或审计清理功能。
- 操作来源是“本机操作（未认证访客）”，没有可信多用户身份体系。

## 二、截图案例：为什么恢复了还不能删

本轮通过只读 API 再次确认：截图中的两个 code 都是 `status=closed`、`lifecycle_state=RESOLVED`，`deletable=false`，原因均为 `ACK_AUDIT_RETAINED`，共享同一个 ACK 周期。

| 北京时间（2026-10-23） | 记录事实 |
|---|---|
| 16:41:14 | 出现溶氧偏低事件 |
| 16:42:04 | 升级为严重低氧，新增该等级的事件行 |
| 期间 | 偏低和严重两个等级分别被确认知晓 |
| 17:11:44 | 两条记录在同一恢复观测下转为 RESOLVED |
| 截图时 | 两行保留历史等级及读数，均显示“历史已知晓”，审计关联阻止删除 |

这个周期一共两次 ACK；不是每行各有两次、总共四次。两行展示的是同一周期共享的人工历史。

标题里的 2.194 / 3.38 mg/L 是记录保留的异常阶段读数，不能当作当前水质。当前页面同时保留红色历史严重等级，却没有醒目区分异常读数和恢复时间，容易被理解成仍有两个异常。

**当前删除保护链路：**

```text
用户 ACK
  → event_actions 保存操作与当时事件快照
  → event_handling_members 关联该周期成员
  → 普通删除与自动裁剪都跳过这些成员
  → SQLite RESTRICT 外键提供额外保护
```

所以反复点击“清理全部已结束事件”不会移除它们，也不应该通过直接编辑 SQLite 或关闭外键绕过。

## 三、为什么用户会感到混乱

| 现有设计 | 用户看到的问题 |
|---|---|
| 底层按 code 保存，列表一行一个 code | 同一次异常像是两件事 |
| 观测状态、等级变化和 ACK 并排展示 | “已知晓”“已消退”“待确认”关系不直观 |
| 结束后的标题和等级保留异常阶段信息 | 红色“严重”和低氧读数看起来仍在告警 |
| 按钮叫“清理全部已结束事件” | 用户合理地认为所有已结束记录都能清理 |
| ACK 关联周期永久受当前普通清理机制保护 | 确认过的事件反而更难整理，列表没有可见的收尾出口 |
| 无归档入口 | 用户只能在“保留在眼前”和“数据库硬删除”之间选择 |

另一个容易误解的数字：`event_limit=300` 不是事件库总数上限。活动关联及 ACK 审计成员不参与这部分普通历史裁剪；持续使用后，受保护记录可以超过 300 条。归档只解决展示整理，不能自动解决数据库长期容量和审计留存期限。

## 四、可以怎样简化：三个方案

| 方案 | 用户获得什么 | 数据处理与成本 | 主要限制 |
|---|---|---|---|
| A：只改列表与文案 | 周期合并、已恢复样式清晰 | 主要是只读投影和前端；可不改 Schema | 有 ACK 的记录依然无法移出历史列表，不能完整解决本次诉求 |
| **B：周期合并 + 已结束归档（推荐）** | 一次风险一行；归档后移出日常列表，可撤销 | 原事件和审计保留；新增持久归档状态，需要明确存储与迁移 | 归档不等于删除，不能减少原业务记录数量 |
| C：允许永久删除已结束周期，包含 ACK | 真正从数据库清除所选周期 | 必须重新批准审计留存策略、定义周期完整删除范围并迁移引用设计 | 可能丢失追溯能力，不能继续承诺这些操作历史永久保留 |

**选择口径：**如果想“页面干净、历史仍可找”，选 B；如果想“数据库里的这批事件和操作记录也彻底消失”，需要选 C，归档不能冒充这种删除。

方案 C 有两种不同的数据合同，实施前必须选定：一是连同该周期 ACK 一起永久删除；二是将审计改为独立快照后只删除事件。这两者对追溯和数据清除的含义不同。当前 `event_snapshot` 已有快照，但仍有必需外键关联，不能据此声称事件现在可以独立安全删除。

## 五、推荐方案 B 的具体体验（未实现）

### 1. 一个周期一行，等级变化放进详情

建议列表示例：

```text
低氧异常 · 模拟池 1
16:41 开始 → 17:11 恢复
已恢复 | 历史最高等级：严重 | 曾确认 2 次
[详情] [归档]
```

- 当前活动异常：显示最新可靠等级和读数；未知时显示证据不足，不回退到旧等级充当当前事实。
- 已结束记录：显示恢复时间，异常数值标为“异常时读数”，历史等级标为“历史最高等级”。
- ACK 操作历史、各 code 的原始事件 ID、批次、等级轨迹都放进详情，不删除底层行。
- 可靠周期按服务端稳定身份整合；无法可靠归族的旧记录按原事件 ID 展示和管理，不凭猜测合并。
- “共 N 条”明确按周期计数；详情另显示包含多少底层记录。合并、筛选和分页须基于全部留存记录，不能只把已加载的 50 行前端拼在一起。

### 2. 页面分成“当前异常 / 历史记录 / 已归档”

| 区域 | 展示内容 | 常用操作 |
|---|---|---|
| 当前异常 | 未结束的风险，包含恢复观察和证据中断 | 查看详情、我已知晓 |
| 历史记录 | 已结束且未归档的周期 | 查看详情、归档 |
| 已归档 | 已移出日常列表的结束周期 | 查看详情、恢复显示 |

首页优先显示当前异常；“最近事件”使用周期摘要，不重复铺出两个等级。已归档记录是否出现在首页应与历史列表一致，并明确标注当前范围，不把隐藏后的列表叫作“数据库全部记录”。

### 3. 用“归档”替代含糊的日常“清理”

- 单条按钮：“归档此已结束周期”。
- 批量按钮：“归档全部已结束周期”，预览明确全设备／全时间还是当前筛选，并显示周期数和涉及事件行数。
- 提示：“移出日常列表，数据和确认历史仍保留，可在已归档中恢复显示。”
- 活动、恢复观察、未结束的未知周期不能通过归档消失；归档不解除 ACK 或引用保护。
- 旧版已结束记录的归档也要核对原结束信息及关联，不能把没有证据的未知事件自动归档为已恢复。
- 已恢复后复发生成新周期，新周期默认可见；归档旧周期不能隐藏后续新异常。
- 如继续保留硬删除，把它明确标为“永久删除未受保护的历史”，放到次要位置；有 ACK 的周期仍按保留策略保护。

### 4. 内部保留准确性，主界面减少状态

主界面建议用“异常中 / 状态待核实 / 已恢复”，恢复观察作为“异常中”的说明，ACK 用次要“已知晓”标签。旧版已结束例外明确保留“旧版已结束（未复核）”，不能为了凑三个状态就当作已恢复。

这些只是显示分组，不修改原 ACTIVE / INDETERMINATE / RESOLVED。等级变化与真正观测未知仍须在详情区分；无可靠新鲜观测时，不能显示“全部正常”。

## 六、持久化、迁移与追踪边界（建议，未实现）

1. 当前没有持久归档字段或归档 API；实现归档需要明确的数据模型，不能仅用浏览器 localStorage 或过滤当前分页假装完成。
2. 可评估独立归档状态表，可靠周期使用稳定周期键，旧格式单记录使用明确的事件 ID；不把归档操作挤进仅允许 ACK 的 `event_actions.action` 约束。
3. 如果归档状态写入 Monitoring SQLite，需要显式 Schema 升级、备份、隔离副本验证和可检查的迁移；不能普通启动时静默改用户库。最终版本号和字段在实施阶段确定。
4. 归档／恢复显示应在事务内重验周期身份、结束状态、成员集合和 revision，避免用户确认期间新观测改变状态。重复请求有明确结果，不自动覆盖冲突。
5. 已归档的审计成员仍受原保护；无审计成员的普通历史仍可能按现有留存上限被裁剪。若承诺长期归档，必须另定持久保留规则；“恢复显示”只对仍然留存的数据有效。
6. 归档、ACK、硬删除、未来人工处理完成分别定义，不能拿其中一个字段代替另一个动作。
7. 不把原始视频、知识库、监测采样历史、Settings、Policy、凭据或 AI 权限夹带进本次简化。

## 七、“手动结束”先不加入本版简化

本轮用户已选择：先整理与修复旧记录，人工结束只做设计，不实施。

未来可以增加独立的“人工处理完成”，表示人工工作结束，同时保留“异常仍持续 / 当前证据不足”的监测状态。操作应绑定周期和等级版本，保存时间、原因、本机操作来源及历史；升级后重新提醒，新周期不继承旧处理结果。

不建议提供把 Monitoring 直接改成 RESOLVED 的普通按钮：它可能人为切断风险周期、隐藏持续异常或造成反复新建事件。先解决一周期多行、历史整理和清理含义，再评估人工工作状态，避免继续向主界面叠加一层状态。

## 八、建议实施顺序与验收

1. 先确认需要的是“移出日常视图”还是“永久删除数据”。未确认前保留现有数据和保护。
2. 在 Prototype 上完成按周期的只读摘要、恢复时间、历史读数及明确计数，先验收页面是否易懂。
3. 如选择 B，再实现持久归档、撤销、后台全量筛选及受控迁移。活动异常和未知观测保护必须保留。
4. 用隔离 SQLite 和合成观测验证，人工认可后才选择性同步 Management；真实实例升级和数据操作另行批准。

最低验收案例：偏低 → 严重 → ACK → 正常恢复，历史只显示一个周期；归档后默认列表移除、数据库原事件和 ACK 数量不变；可恢复显示并在服务重启后保持状态；恢复后复发的新周期仍出现；活动／缺测／离线不能被误归档；旧格式无可靠结束证据时仍受保护；过期 revision 被拒绝；桌面和 390px 页面正常。

**推荐决策：先做方案 B 的交互与只读周期摘要，再做持久归档；暂不放开 ACK 永久删除，暂不增加人工处理完成。**如果用户明确要求真正减少数据库中的事件和审计记录，则改为讨论方案 C 的留存策略，不能只交付归档。
