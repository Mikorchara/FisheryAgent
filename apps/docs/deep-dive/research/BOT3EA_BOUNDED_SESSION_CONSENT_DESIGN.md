# BOT-3E-A：受控持续会话授权设计与架构审计

后续进度：本设计已获用户批准，3E-B的Fake-only实现见[离线持续授权](../../patches/2026-10-31-stages/BOT3EB_BOUNDED_SESSION_OFFLINE.md)。下文保留A阶段审阅事实和当时停止点，不代表B已开放真实执行。

审阅日期：2026-10-27（北京时间）。项目：`Fishery_AI_Prototype`，`main / e8c9654`；开始时工作树干净。

**本轮仅完成3E-A，不实施3E-B/C。** 从逐Turn人工批准改为会话级授权，需要新的批准类型、额度原子消费、运行所有权和成本合同，触发任务附件“审批、Scope或成本合同重大改变时先提交方案并停止”的条件。没有修改运行时代码、发布资格或旧批准，没有读取真实密钥/业务实例，没有连接QQ/Qwen，没有修改Management，没有commit/push。

用户在任务附件中确认了BOT-3D-2C的真实双轮验收、客户端显示及机器报告结果。本轮将其列为**用户提供的验收证据**，未重读原始聊天、私有运行报告或云平台账单，也不把一次成功扩展为长期运行保证。

## 1. 结论与推荐范围

现有Gateway、只读Monitoring、Agent、Scheduler、DeliveryOwner和内存历史能够支撑小规模持续问答；不需要Redis、微服务、第二套Agent或新的聊天数据库。需要更换的是“运行许可与额度”的上层合同，不能把旧双轮的2直接改成5、600秒直接改成1800秒。

建议首版候选：最长30分钟、最多5次**AI准入许可**、每轮最多2请求/512输出Token每请求/90秒/零重试，保留1个AI worker、2个等待位置和每会话单飞。一次许可不保证一次成功回复或真实扣费；失败、取消、未知结果可能消耗许可。

首版保持固定Qwen、当前水质只读Tool、SIMULATOR来源、原A/B/C封闭解释。建议先限制一个明确实例/设备/群，允许从现有白名单中**显式选择**少量成员（候选1～4人），共享总额度。默认复用既有request中的单成员，不自动把整个access白名单纳入批准；多群、多设备留后续独立Scope，不必首版通用化。

需人工审阅后才能开始B：

1. 接受“仅本次进程运行，崩溃/重启不续用旧批准”，还是要求断点续跑；推荐前者。
2. 保留现有保守预留，还是另行研究更小但可证明的输入费用边界；本方案推荐先保留。
3. 确认共享成员范围，以及模型失败/未知交付时是否继续接受新消息；推荐下文分级故障策略。

### 不能直接复用的合同

- `ConversationTrial`只支持一个`_active`和一个`_ready`，且未verified就停止整个试用。多成员排队需要有界的per-Turn lease映射，不能只循环调用旧`approve()`。
- `plan()`要求`state.turns == len(self.turns)`；持续模式中清空、TTL过期、内存淘汰会减少历史，但不能减少已消耗额度。预算账本必须独立于历史长度。
- [channel_conversation_trial.py](../../../ai_service/channel_conversation_trial.py):18起把两轮、600秒及逐Turn批准写入Scope；`ConversationQwenTurn`的父类精确要求`QwenTrialApproval`。不能伪造旧批准对象或放宽为任意duck type来承载会话许可。
- Service、Scheduler、Router、Gateway、Transport均有精确装配类型门禁。新增Run类型需显式审核接入，而非修改`can_send/can_deliver`。
- 现有`SDK_RESOURCES`是进程内资源门禁，不是跨进程的费用/次数账本；不能用它代替运行所有权。

### 准入顺序的改造点

`QQAIJobScheduler.submit()`目前先执行`coordinator.prepare()`，再检查队列容量及单飞；而双轮`prepare → begin`已经消费批准。当前单成员双轮的限制降低了触达此路径的机会，但这个顺序不能原样迁到多成员共享额度，否则BUSY也可能消耗额度。

建议拆出不消费的准入检查/上下文冻结，在Scheduler容量与单飞检查通过后，才原子预留Run额度并创建本轮执行lease；随后入队。预留之后若发生失败，不退款。锁顺序须固定，不能在配额锁内等待网络、模型、交付或人工输入。

## 3. 新Session RunConsent与TurnLease（设计，未实现）

候选合同建议名：`qq-qwen-bounded-session-trial@1`。**本轮未创建对应JSON、实现指纹或可执行资格。**

RunConsent一次批准以下内容：

- 新的consent_id、批准时间、绝对期限、最长单调时钟运行时长、当前进程生成且不能从CLI恢复的run_nonce。
- 固定Provider/Preset/模型、Prompt/Tool/历史/交付/SDK资源合同及源码Scope摘要、静态价格/预留算法版本。
- 明确的实例/设备/群/成员选择、现有access/AI/Policy交集及绑定版本；批准的是名单快照，不是“所有未来白名单用户”。
- 最大AI准入数N、最大保留模型请求数2N、单轮90秒/每请求512输出Token/零重试、总预算及每轮预留额。
- QQ与Provider独立联网同意、SIMULATOR及投影历史披露、受限解释、SDK线程/远端计费风险、本机操作者来源。

每轮由程序从有效RunConsent派生**内部TurnLease**，不是再伪造一份人工批准。Lease绑定父consent摘要、序号、原消息键、成员/设备、当时权限与会话快照、请求/金额预留、截止时间及独立Handle；不能从QQ正文或任意JSON直接构造。

Scope绑定静态合同和批准配置；剩余额度、成功次数不是Scope内容，否则每轮递减都会使整个Scope/历史失效。原单轮/双轮批准、Provider回执和发布资格不能转换成RunConsent。

清空会话只使本成员的旧历史快照和在途任务失效，不续期RunConsent、不退还额度、不清除消费账本。历史过期或新话题也不补充额度。

## 4. 请求与费用预算：现有算法的实际结果

直接调用当前`channel_trial.cost_reservation()`复算，而非按历史Usage外推。代码中的静态口径为：每请求预留1,000,000输入Token，输入0.8元/百万、输出2.7元/百万，512输出Token，最多2请求；向上取整到0.000001元。

```text
R = ceil_0.000001((1,000,000 × 0.8 + 512 × 2.7) × 2 / 1,000,000)
  = 1.602765 元 / AI准入许可
5 × R = 8.013825 元
floor(2.00 / R) = 1 轮
```

| 方案 | 上限与含义 |
|---|---|
| 保留算法，最多5轮 | 10请求上限；至少8.013825元本地预留，若以分为单位填写可选8.02元；这是候选方案，不是自动增加用户预算 |
| 保留2.00元总预算 | 最多预留1轮，不能宣称支持5轮；减少最大Turn数后再批准 |
| 希望2.00元支持5轮 | 必须另审更小的输入上界/预留算法；不能直接根据0.006382元历史估算退还预算或按“平均用量”预支 |

建议启动时要求`总预算 >= N × R`，不足就拒绝计划并解释，不静默把“5轮”变成1轮。审批摘要同时显示每轮/总预留和最大请求数。

代码中的价格是**既有静态合同，不是本轮核实的最新报价**；联网前仍需人工核价。32KiB请求体和4KiB历史投影有助于控制输入，但不是已证明的Provider总Token/费用上界；不能据此直接下调预留。

运行中用整数微元或Decimal记录，不用float。成功、已消费许可、保留请求数、实际SDK请求、HTTP尝试、完整Usage估算和Provider账单必须分别统计。首版不依据实际Usage自动释放差额；失败、取消、未确认费用都按完整R与2个请求槽保守计入。

本地预算约束的是应用准入和已声明的计价口径，不是云平台账单硬封顶。网络超时、远端继续计算、计价变化及云端账单差异仍需外部账户限额与人工核对；本轮不调整云平台设置。

## 5. 原子消费、跨进程与崩溃

推荐首版：**一个批准只绑定当前运行，绝不跨重启续跑**。因此无需新增SQLite预算库或持久聊天库；内存额度 + 小型脱敏写前消费日志即可，但日志不能被当作可恢复余额。

```text
认证/意图/权限/消息时效 → 去重 → 队列与单飞检查
  → Run锁内：复核Scope/权限/期限/所有权
  → 校验N、2N与总预算 → 记录唯一消息键和本次完整预留
  → 写前日志flush/fsync确认 → 提交内存消费并签发TurnLease
  → 私有Service/Handle入队 → 原模型/Tool/交付流程
```

任意写前日志失败、写入结果未知或状态冲突，Run进入fail-closed，不启动本次模型、不回滚补额度。崩溃在“已预留、尚未执行”之间也损失该许可；这是保守策略，不伪称已经扣费。

### 运行所有权

1. 进程内使用同一RLock串行预留；多成员不能各持一份总余额。
2. 批准必须绑定当前新生成的nonce，构造器/CLI不接受从旧批准恢复nonce；新进程拒绝旧RunConsent，即便旧used文件被复制、改名或删掉。
3. 仍建议在固定可信状态位置为consent摘要执行create-only启动声明，并持有Windows独占运行所有权句柄。普通`write_new()`只保证拒绝覆盖，**不等于防止删除**；若需要运行中拒绝重命名/删除，应使用明确的不共享write/delete的原生文件句柄，并在新合成目录做双进程测试。
4. 所有权或声明状态变化立即停止准入；消费日志不完整不得“修复后继续”。崩溃后不重放旧消息、不恢复余额、不自动新建批准。

本方案防止正常程序的重复启动/重放与状态丢失后意外补额度；不声称能抵抗拥有同一Windows账户权限的人修改源码/内存，或管理员终止进程、回滚整个文件系统。没有独立可信服务或硬件根时，本地文件无法提供绝对防篡改。若要求离线批准跨重启恢复并抵抗这些攻击，需要另一个安全设计，不在最小版本内。

### 去重必须比短消息缓存更长

现有Adapter按消息300秒、会话900秒清理；30分钟Run不能把短缓存当成消费账本。对进入模型准入的消息键（App/群/msg_id）及内容/成员指纹，至少保留到本Run结束，最多N条，重复不再次预留或推理，冲突拒绝。原QQ被动回复时限及单次Owner继续保留，不延长平台窗口。

## 6. 记忆、多成员与到期

现有ConversationStore足够首版。运行30分钟不等于记忆保留30分钟；继续15分钟空闲TTL，超时后追问澄清或重新查询，不延长旧事实有效期。

多成员：1个AI worker、FIFO有界排队、每个完整身份会话最多一个排队/执行/待交付任务；各自历史隔离，总额度共享。没有权限的成员、伪造Mention、问候/帮助/澄清、队列BUSY均不产生模型预留。合法成员可能先用完共享额度；是否分成员限额属于另一个需批准的产品规则，首版不暗加。

应区分两个检查：

- `can_admit()`检查剩余额度，零余额时只拒绝新AI任务。
- `check_existing_lease()`检查当前任务已预留的权利、权限、Scope、期限与SDK状态，不能因剩余额度变零取消最后一个合法任务。

每轮期限取“准入起90秒、Run绝对/单调期限、原消息回复窗口减15秒”的最早值；等待最多10秒。Run到期取消未完成任务，按既有有界清理保存报告后退出。预算先耗尽时可在仍有效的QQ/数据授权期限内保留固定只读命令和零费用提示，不能隐式续期。

## 7. 故障与退出策略（待审）

| 情况 | 建议首版策略 |
|---|---|
| 源数据stale/offline/缺测 | 继续原有限事实与限制展示，不把未知当正常；不因聊天记忆替代本轮Tool |
| 模型失败/超时，但本地SDK关闭明确 | 消耗已预留额度，无成功历史；可接受下一条新的授权消息，不自动重试旧任务 |
| QQ送达未知 | 保留检查点，不发第二次回复、不提交成功历史；不补额度。可等待下一条独立消息，不能重放旧消息 |
| Gateway断线 | 按原规则取消任务并保守消费；只复用既有有界Gateway重连，恢复后仅处理新的有效消息 |
| SDK关闭失败/状态不明 | 停止整个Run的AI准入，取消任务，保留sticky隔离；不因余额尚有就创建新SDK请求 |
| 权限/Policy/Scope/实例设备变更 | 使旧Run失效并取消任务，不能热更后继承剩余额度；固定查询也需重新满足自身权限 |
| 配额/所有权日志失败 | 整个Run fail-closed，不启动该模型、不自动修复余额 |
| 交付检查点/结果持久化失败 | 保留实际API接受状态，不重发、不重新推理；首版建议停止新AI并输出安全错误 |
| 正常期限/Ctrl+C | 停准入、取消、关闭I/O、加入线程、保存最终报告、清空RAM；强杀/关窗仍不能保证最后一次写盘 |

“普通单轮失败后允许下一条新消息”区别于当前双轮Host的任意未verified就全停，需要显式审查并测试。可先采用更保守的“任何执行失败停止本Run”，但不应把它宣传成健壮的长期助手。
