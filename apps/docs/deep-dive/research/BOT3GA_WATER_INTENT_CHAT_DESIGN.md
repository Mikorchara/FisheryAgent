## 2. 现有路由与安全边界

实际链路：

```text
认证 QQ 群 @ → 入口白名单/时效/去重/限流
  → 固定命令优先
  → Mention 证明 + 当前 AI/群/成员/设备权限 + 会话绑定
  → classify(正文, 已接受历史的最后 focus)
      ├─ 模板/澄清/拒绝：原被动回复 Owner，零模型、零 AI Turn
      └─ water：Scheduler 容量/单飞 → RunConsent 原子预留
          → 私有 Service/Handle → 原 Agent → 本轮 Tool → 两次模型请求
          → Source/Commit/SDK 门禁 → 封闭解释 → 发送前复核
          → API 接受 → History Commit
```

依据：[intent.classify](../../../qq_bot/intent.py)、[Router._receive](../../../qq_bot/ai_routing.py)、[Coordinator.prepare](../../../qq_bot/ai_coordinator.py)、[RunLedger.reserve](../../../qq_bot/run_consent.py)。

- `classify()` 只是有限字符串路由，不是权限或付费授权。`water` 结果还必须通过所有准入检查；未知 slash 命令不会自动变成 AI。
- 默认 Command Mode、固定命令和旧试用入口不在本设计中扩大。以下矩阵针对已独立授权的 Mention + Memory Session。
- 自然语言模板也经过身份、Mention、当前授权及发送前检查；**免费不等于匿名或无限频率**。显式 `/问AI` 在会话路径中也会经过 classify，不会自动绕过澄清。
- 当前 focus 只有 `all / temperature_c / ph / dissolved_oxygen_mg_l`。用户原句被 [question_for](../../../ai_service/channel_conversation.py) 改写成服务器规范问题；“水质可靠吗”和“为什么不能确认水质正常”最后得到同一句规范问题，模型并不知道二者语气目的不同。
- [ConversationStore](../../../qq_bot/conversations.py) 保存实际已接受安全答复，但进入 Agent 的历史只是 focus、来源时间和有效性投影，不包含完整原始问题、读数或一般代词推理能力。可理解“上轮谈溶解氧”，不能据此知道新的水质或恢复已失效的权限。
- 每个需要本轮事实的 AI Turn 仍查询 Monitoring；模板若不读取 Tool，就只能讲条件性原理/能力边界，不能断言当前确实缺测、过期、正常或低氧。

## 3. 七类问法：现状与建议

下表“2 请求”表示正常单轮最多 2 次模型请求，准入后保守消耗 1 Turn / 1.602765 元许可；不是每次实际账单。无授权、BUSY、限流、重放等拒绝不能因此扣额度。

| 用户原问法 | 当前，无话题 | 当前，有已接受溶解氧话题 | 建议 BOT-3G-B（尚未实现） | 费用变化 |
|---|---|---|---|---|
| 现在的数据可靠吗？ | clarify，0 | 同左 | 当前 Tool，focus=all；描述本窗口质量/时效/连接，不能担保传感器准确度 | **0→1 Turn / 最多2请求** |
| 有没有低氧风险？ | clarify，0 | 同左 | 当前 Tool，focus=溶解氧；只解释本轮领域 finding，stale/offline 时明确未能评估 | **0→1 Turn / 最多2请求** |
| 为什么不能确认水质正常？ | water/all，2请求 | 同左 | 保持本轮查询；用来源限制解释无法完整确认，不编造先前原因 | 已可能收费；请求上限不变 |
| 当前监测数据是不是过期了？ | clarify，0 | 同左 | 当前 Tool，focus=all；依本轮 freshness 与时间回答 | **0→1 Turn / 最多2请求** |
| pH缺测会有什么影响？ | water/ph，2请求 | 同左 | 优先免费条件性模板：“若 pH 缺测，不能完整判断酸碱状态；这不说明当前设备确实缺测。”明确“当前pH是否缺测”等才查询 | 此通用原句建议 **2请求→0**；具体当前查询保持收费 |
| 那现在应该怎么办？ | clarify，0 | water/溶解氧，2请求 | 没有稳定话题继续澄清；有授权话题则重新查询，只给封闭建议代码支持的核对/上报建议 | 保持条件收费，不自动补猜话题 |
| 现在适合养鱼吗？ | clarify，0 | 同左 | 免费能力边界模板；不能作养殖适宜性、健康或安全保证，提示可查询当前水质 | 0→0 |

表中三处 **0→AI** 的变化必须明确批准，即使 Run 最大 Turn、费用算法和工具完全不变，也扩大了会产生费用的输入集合。不得以“只是补同义词”为由直接上线。反向的免费模板改变和更早的能力拒绝也要纳入新路由 Scope。

未来启动摘要应列明这些新增可收费问法；每 Run 的既有上限、共享额度和失败不退款不变，但自然表达更容易触发模型，额度可能更快耗尽。不得把“每轮调用数没增加”说成“用户费用行为没有变化”。

### 相近说法的实际差异

本轮测试集有 36 种表达、无历史/有已接受溶解氧话题两种条件，共 72 项现状投影：

| 同类表达 | 当前实际结果 | 问题 |
|---|---|---|
| “水质数据可靠吗？” | water/all | 加上“水质”就可能收费，与“数据可靠吗”不一致 |
| “溶氧会不会过低？” | water/溶解氧 | 含完整指标词能进入，只有“低氧”却不能 |
| “当前pH数据是不是旧的？” | water/ph | 会查询，但没有独立 freshness 意图 |
| “pH缺测是什么意思？” | unsupported | 通用“是什么”拒绝先于 pH 匹配，连条件性缺测说明也被挡住 |
| “那为什么不能确认水质正常？” | 两种话题条件都 clarify | 先进入 follow 分支，又无显式指标/“现在”，不能靠后面的“水质”补救 |
| “那溶解氧该怎么办？” | 无历史 clarify；有话题 water/溶解氧 | 即使显式指标存在，当前 follow 规则仍要求历史 |
| “现在水质适合养鱼吗？” | water/all | 会收费，但最终仍只能答当前水质，不能回答养殖适宜性 |
| “请介绍水质助手功能” | water/all | “水质”优先于能力说明，可能产生用户不预期的模型调用 |

这些是当前覆盖与准入体验缺口，不是越过授权；成功进入 AI 也不代表已经回答原句全部语义。本轮没有通过调整 production classifier 消除它们。

## 4. 最小职责划分与分类顺序

### 不新增通用意图模型或 Agent

1. **固定命令**：继续交给原固定查询，优先级不变。AI 历史/Knowledge 未开放不影响已有明确固定命令的独立权限合同。
2. **受限程序模板**：问候、能力说明、泛化的 pH 缺测影响、超能力的养殖适宜性说明。模板没有现场事实，不冒充 Tool 结果，不提交成功 AI 历史或扣 Run 额度。
3. **本轮当前 Tool + 原 Agent**：可靠性、当前低氧风险、时效和不能确认的当前原因；复用当前水质唯一入口，完整保留权限交集和原 1/1/2 循环。
4. **会话追问**：只继承当前授权话题 focus；没有话题、过期、清空或改绑时澄清。不得从历史取旧数值回答“现在”。
5. **证据不足**：不是固定一律拒绝调用；允许查询得到 stale/partial/NO_DATA 后，明确“当前不能判断”，不能强行生成确定性结论。养殖适宜性、治疗、控制则不因数据完整而转为允许。

建议沿用现有 kind/focus 路径：在 `intent.py` 先对有限的能力/条件性说明采用模板，再加入明确“当前数据可靠性/时效/低氧”表达。拒绝写操作、设备切换、知识/治疗等保护仍先于这些模板与业务路由；不能用“pH”片段盖过同句中的“删除/控制”。

第一版**不增加 purpose 历史字段、不改 Agent Prompt、不引入新的 JSON 解释枚举**。新同义表达落到现有 focus 和规范问题；展示依当前 SourceSummary 给出本窗口状态。若后续需要回答更细的因果或跨主题代词，应单独设计，而不是把未审查的原始问题/历史塞入 Prompt。

新增模板可在原 Router 的非 water 分支返回，不需要第二套网络发送器。模式、模板/路由实现依然要绑定 Scope；一次性计划/审批不能从旧 Run 继承。

### 规则与来源边界

- “数据有效”只说明现有合同校验；即使 fresh/valid/online，也不能宣称硬件精度、养殖条件或专业诊断已经验证。
- `stale/offline` 时按 [rules.assess_channel](../../../monitoring/rules.py) 不评估当前风险；过期 2.2 mg/L 不能自行转成低氧 HIT。fresh 低氧也必须来自真实领域 finding，不在 router/renderer 复制阈值。
- 没有 HIT 分两种：可靠当前窗口未命中实验规则；证据不足未能评估。不能统一写“没有风险/全部正常”。
- [SourceSummary.from_result](../../../ai_service/channel.py) 与 [assess_explanation](../../../ai_service/channel_presentation.py) 保持权威：模型只选有据的引用/建议，不能创造读数、阈值、事件或“已处置”。

## 5. Chat 文案合并设计（未实施）

当前 Chat 已明显短于 Detailed，但 [BOT-3F-C](../BOT3FC_REAL_ACCEPTANCE_PERFORMANCE_REVIEW.md) 的两条真实正文仍有 7 行完全相同，追问只少 11 字符。可合并状态和机械建议；每条仍必须自带限制，不依赖前一条消息。

对照使用该已验收正文中的留存值，仅作为设计样例，**不是本轮重新查询/真实发送结果**：

```text
SIMULATOR 模拟数据 · sim-pond-1
溶解氧：2.2 mg/L（留存值）
数据过期、设备离线，pH缺测；当前水质与风险无法完整确认。
AI 建议（已校验，未执行）：检查上报并核对后续观测。
观测 2026-10-25 02:55:28；评估 2026-10-27 23:48:07（北京时间 UTC+08，未重新采样）。
```

此样例的“已校验”标签只有未来真实沿用封闭建议校验通过后才能呈现，不因本文样例获得执行资格。建议合并映射仅取已通过 `_Plan.advice` 中的代码组合：如 verify_observation + check_reporting 合并为一条；若只有其中一项，不擅自追加另一项。

保留项：SIMULATOR、设备、指标/单位、观测与评估时间及北京时间、缺测/invalid/unknown/stale/offline、未重新采样、所有严重规则 HIT、系统事实与 AI 建议边界。严重 HIT 独立保留，不随 focus 隐藏；没有 HIT 且证据不足时不写“未触发/已恢复”。

不做：跨消息省略来源/限制、从 2.2 自建阈值判断、自由文本放行、发送“正在查询”第二条消息、额外模型/DB 请求。无效计划仍退回可信事实；长度不足仍不能截掉关键限制。Detailed 保留原 A/B/C 内容与默认选择语义。

### 预期安全回归覆盖

- 当前查询、明确追问与话题切换每 Turn 分别查询 Tool，两次模型请求上限不变。
- fresh/valid/online、pH缺测、stale/offline、新鲜低氧 HIT、同值过期低氧未评估。
- 未授权成员、撤权、伪造 Mention、重复原消息、额度耗尽和限流拒绝均不额外消费许可/推理。
- SDK 隔离、配置同 mtime 变更、发送前撤权、API接受后撤权与历史哈希继续由原相关专项复核。

## 7. Scope、风险与 BOT-3G-B 计划

本轮 186 个已跟踪的生产源码、配置、资源和脚本文件字节摘要集合前后完全一致；重新计算的 Chat/Detailed 准备资源均与现有 candidate 一致。当前 Chat Scope 仍为 `cef647bcd2c43f8bf8b9da7a1e2e3104c8fac56204c3b1e070cd95a3938cd4d0`。未修改任何资格、真实批准、used 或历史回执，也未开放新路由。没有因本轮文档/测试修改而作废或迁移旧资格；旧进程 RunConsent 本来就不能复用。

真正实施时，`intent.py`、Chat renderer 均已在现有实现图中绑定；FAST、TwoTurn、Fake Conversation、Session candidate 及真实试用派生 Scope 都要重新计算受影响部分，不能只刷新 Chat 一个 JSON。Detailed 即使输出不变，也可能因共享路由实现摘要变化而需重新审批。旧批准/回执不改写、不当作新代码许可；所有门禁保持。
