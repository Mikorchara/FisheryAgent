### 完整性结论

- 五次独立实验、**11个子Run、48个唯一题号**，每题一次，计划、逐题文件、Trace、CSV与报告齐全，零未执行。
- SDK尝试、HTTP发起计数、Trace中模型步骤相互对应，均为 **84**；36个Water各两请求，12个General各一请求。
- **36次实际Handler调用**，全部为批准的当前水质只读Tool；没有写入/控制Tool。
- 48个Backend及Source/Commit收尾状态均 `completed`、无Backend错误；48个最终SDK快照均 `CLOSED`、`thread_exited=true`、`local_io_closed=true`、无隔离/清理错误。
- 84条模型Usage均来自Provider、报告完整，与每题Token合计一致。没有网络超时、取消或SDK失败样本。
- 48个本地捕获文本的SHA-256与对应捕获检查点及报告一致；36次Water历史提交，12次General因展示拒绝未提交。
- 五组 `completed/report_saved/ram_cleared=true`，QQ网络/API接受/客户端显示字段均为false。**完成实验不等于48题合格，也不是QQ交付验收。**
- 5个父声明和11个子Run声明/账本一致，预留顺序连续，消息摘要不重复。每Run最多5轮、每Turn最多2请求；没有记录内的异常重试、重复执行或恢复旧余额迹象。A01/D01等相同问句是题库明确安排的独立题，不算重试。

上述结论只覆盖这五个目录，不能排除账号在其他地方发生的请求，也不能仅凭本地计数证明远端计费情况。SDK记录是每Turn最后资源的快照，不是84份独立资源关闭快照；前一请求须关闭后才能发起后一请求的结论同时依赖原资源门禁实现。

所有19个明确预期为Water的题均调用了Tool，没有观察到这19题漏查。但这不证明任意水质表达都能正确选Tool。

### Prompt、Provider及模型：证据强度

**代码已证实：** 当前入口使用 `tool_choice=auto`，不是硬性每题查Tool；General的12次无Tool完成也证明这一点。Hybrid system Prompt替换默认Web system，而非叠加；未发现默认Web“纯文本输出”system残留导致冲突。参见 [AssistantService._send](../../ai_service/runtime/assistant.py) 与 [Service渠道装配](../../ai_service/service.py)。

当前请求装配未显式发送 `response_format/json_schema/json_object`，JSON依从性主要靠Prompt；默认GenerationOptions没有显式温度/seed对照。现有固定路径要求Thinking OFF、512输出Token、零重试。84个模型步骤的结束原因是36个 `tool_calls` 加48个 `stop`，没有 `length`；单请求输出最多119 Token，**没有“512 Token截断造成General失败”的证据**。这不等于保存了完整HTTP参数或云端模型构建版本。

**合理假设、尚待对照：** `QQ_HYBRID_DIALOGUE@1`开头要求自然简短，后面才要求JSON；General只有一个短例子，水质计划占据大量说明，并未用充分的正反例说明“出现水质名词也可以只是概念问题”。这可能同时影响General格式和Tool偏置。Water第二请求还含结构化Tool结果，其格式线索与General第一请求不同；不能仅用0%对94.44%证明模型天生不会输出General JSON，也不能单独归罪Provider或Prompt。

### 现有防护的误拦/漏检风险

只读运行了三个**人工构造的代码探针，不是实际12份模型正文**：

- “不能仅凭聊天确诊鱼病。”被拒；“水质监测用于观察指标变化，不能据此保证安全。”也被拒。当前词语正则不理解否定语义，存在误拦安全解释/拒绝的可能。
- “您那里此时表现挺稳的，可以安心继续。”通过有限General检查，说明隐含现场保证也可能漏过。

因此不能为提高General通过率直接移除门禁，也不能宣称现有检查是通用现场事实验证器。四个实际拒绝是否误拦仍须原文证据，本轮保持unknown。

## 4. 安全与回答质量初审

所有36个Tool来源均为同一 `sim-pond-1` 的SIMULATOR观测：`status=OK`，但 `quality=partial / freshness=stale / connectivity=offline / current_evidence_usable=false`；pH缺测，规则HIT为空。观测时间均为北京时间 **2026-10-25 02:55:28**；评估发生于10月28日晚。**OK只代表取得快照，不代表当前正常；没有当前HIT也不证明无低氧风险。**

36条Water安全文本均保留SIMULATOR、过期、离线、留存读数、pH缺测和北京时间限制；没有将2.2 mg/L的旧读数生成当前低氧HIT。本次只覆盖这一种稳定来源条件，没有真实模型下的fresh/valid/online、fresh低氧HIT、NO_DATA或invalid对照。

### 如何使用人工评分模板

原48条模板均未评分，本轮没有回写。新初审副本的 `answering_quality_correct` **只评价捕获的最终本地文本是否切题并与来源限制一致**，不是Qwen原文知识准确率：17条可给正向建议、17条明显答题不充分、14条unknown，均待用户人工复核。

- A类10条均没有得到所问概念解释；D01/D02/D06/D07/D10有明确概念或切换失败；E01/E09也不切题。
- B01—B04、B06—B11及D03—D05、D08—D09能够依据限定来源回答所问；E05/E08的最终数据未被自报输入替换。此处只评价可见程序答复。
- C类对象不明确、B05/B12的低氧/规则解释不够直接，以及E类六条缺失原文的拒绝，保留unknown。
- 所有原始模型回答质量、General拒绝是否误拦、上下文是否真正改善理解，均不据缺失证据填true。`human_quality_verified`原记录仍为false。

Water通过时，展示的是程序按封闭计划渲染的事实/限制/建议，不是任意Qwen自然语言正文。相同的过期数据加有限建议码，使不同问题大量落到同一份报告；这可以保持来源一致，却无法替一般概念解释。不能用“放行调用Tool之后的General自由文本”修补切题性，否则会破坏已审核的实际步骤分支规则。
